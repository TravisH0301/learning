# Json Web Token (JWT)
JWT or JSON Web Token is string of characters used to transmit information between partises as a JSON object.

## Use Case
- Authorisation: Most common scenario for using JWT. Once the user is logged in (authenticated), the server issues a JWT for the user including the role, permission, expiry time, etc.
- The user/client then uses this JWT in their HTTP authorisation header to access routes, services and resources that are permitted with this token.
- Information Exchange: JWT is a good way to securely transmit information between parties, because JWT can be signed, ensuring the receiver know the senders are who they say they are.

## Structure
JWT is a combination of 3 fields:
1. Header: tells which algorithm is used and type of token
```
{
  "alg": "HS256",
  "typ": "JWT"
}
```
2. Payload (Claims): user data like id, role or department
```
{
  "sub": "1234567890",
  "name": "John Doe",
  "admin": true,
  "iat": 1516239022
}
```
3. Signature: proves the token is authentic

These components are encoded in Base64Url (making it compact & url-safe) and concatenated with a "." as shown below:

## Signature
The aim of JWT is not to hide the data in any way but to add authenticity of the data
to prove that the sent data was actually created by an authentic source. Although payload can be encrypted for security (e.g., JWE).

The signature of the JWT can be generated in two ways.
- MAC (Message Authentication Code) using a symmetric key with hash algorithms
- Digital Signature using asymmetric keys with signature algorithms

### MAC with Symmetric key
JWT can be signed with a symmetric secret key using a cryptographic hash algorithm (e.g., SHA256) 
that creates a HMAC (Hash-based Message Authentication Code) as a signature.

#### Geneartion
The signature is generated by passing both encoded header and payload with a secret key to the HMAC hash algorithm as following:
```
HMACSHA256(
  base64UrlEncode(header) + "." + bsae64UrlEncode(payload),
  secret
)
```

#### Verification
A receiver of the signed JWT can verify the signature by comparing it with its own version of the signature. This involves:
1. Generate siganture using HMAC hash algorithm using the encoded header and payload of the received JWT with the secret key
2. Compare the generated signature against the signature of the received JWT

If the signatures match, it verifies that the JWT was not tampered during the transmission.

### Digital Signature with Asymmetric keys
On the other hand, JWT can be signed using a private key and verified using a public key 
with the use of digital signature algorithms (e.g., RSA [Rivest-Shamir-Adleman], ECDSA [Elliptic Curve Digital Signature Algorithm]).

#### Generation
The JWT is signed by the sender/issuer with a private key. This involves:
1. Hashing the encoded header and payload
2. Signing the hashed value using digital signature algorithm with the private key (RSA encrypts but ECDSA mathematically calculates)

#### Verification
The receiver can verify the JWT by:
1. Determine the hashed value of the encoded header and payload from the received JWT's signature with the public key (RSA decrpytes but ECDSA mathematically calculates)
2. Generate a hashed value using the encoded header and payload of the received JWT
3. Compare the above two hashed values

If identical, the JWT has not been tampered.

### JWT Signing Comparison: MAC vs. Digital Signature

| Feature | MAC (Symmetric - HS256) | Digital Signature (Asymmetric - RS256/ES256) |
| :--- | :--- | :--- |
| **Algorithm** | HMAC + SHA256 | RSA or ECDSA |
| **Key Type** | **Single Shared Secret** | **Private Key** (Sign) + **Public Key** (Verify) |
| **Authority** | Anyone with the secret can both sign and verify. | Only the issuer has the Private Key; anyone can verify. |
| **Performance** | **Very Fast** (low CPU overhead). | **Slower** (computationally expensive). |
| **Key Distribution** | Secret must be shared with every verifying server. | Only the Public Key is distributed; Private Key stays hidden. |
| **Ideal Use Case** | Small apps, Monoliths, or internal private APIs. | Microservices (MSA), SSO, and Public/Third-party APIs. |
